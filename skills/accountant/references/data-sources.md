# Data sources

What the counter reads, how it reads it, and what it therefore cannot know.

## Where the data lives

```
<DSH_HOME>/sessions/<slugified-cwd>/session-<uuid>/session.v4.jsonl.zstd
```

`DSH_HOME` is `%USERPROFILE%\.dsh` on Windows and `~/.dsh` elsewhere. Override
with `--data-dir`. One file is one session; the directory name carries the
workspace, the file name carries the session id.

## How a log is encoded

Append-only, one write per frame, each write a **separate zstd frame** holding
one or more newline-delimited JSON records. Concatenated frames are legal zstd,
but `zstdDecompressSync` and the streaming decoder both stop after the first
frame — so a naive read returns only the session header and reports zero usage.

The counter therefore scans for the frame magic `28 b5 2f fd` and decodes each
frame with the bytes up to the next magic. Two consequences:

- A frame still being appended at read time fails to decode and is skipped. It
  is picked up on the next run.
- A four-byte magic inside a compressed block would split a frame. The odds are
  about one in four billion per position, and a mis-split frame is dropped
  rather than corrupting the totals, so the failure mode is one lost record,
  not a wrong report.

## The records that matter

| Record | Fields used |
|---|---|
| `session` | `id`, `cwd`, `agentPreset`, `delegationDepth`, `createdAt` |
| `assistant/message` | `time`, `data.usage`, `data.message.source.{provider,model}` |

`data.usage` is the provider's own accounting:

```json
{ "inputTokens": 962, "outputTokens": 116, "cacheReadTokens": 8960, "cacheWriteTokens": 0, "totalTokens": 10038 }
```

`totalTokens` is the sum of the first four. The counter ignores that field and
sums the components itself, so a changed field cannot silently double-count.

`inputTokens` are prompt tokens that missed the cache, billed at the miss rate.
`cacheReadTokens` hit the cache, billed at the much cheaper hit rate. This
distinction is the single biggest driver of the dollar figure, which is why a
cache-heavy day can move far more tokens for a fraction of the cost.

## What is not counted

- **Session titles.** Generated by a separate model call recorded as
  `session/title-llm-request`, with no `usage` payload.
- **Compaction summaries.** Recorded as `compaction/summary`, likewise without
  per-call usage.
- **Some retries.** A retry that never produced an assistant message leaves no
  usage record.
- **Search and Fetch.** Metered per request by DeepSeek, not per token.
- **Traffic on the same key outside DSH.**

Together these make the total a floor. For an individual power session the gap
is usually well under a percent; across months of cheap title calls it stays
small but not zero. Never call the number an invoice.

## The cache

First run parses every log: a few hundred megabytes and several seconds.
After that, results are cached per file, keyed by absolute path, byte size, and
mtime, and only changed files are re-read. Steady-state runs finish in well
under a second.

The cache stores **tokens only**, bucketed by UTC day, UTC hour, and model. It
stores no prices, no timezone, and no tariff decision. That is why changing
`--rate`, `--tz`, or the holiday list re-prices instantly instead of
re-scanning: only tokens are cached, and money is computed fresh every run.

Location: `<DSH_HOME>/cache/accountant/usage-cache.json`, written atomically via
a temporary file and a rename. Delete it any time with `--clear-cache`; a
corrupt or missing cache is treated as empty and rebuilt, never as an error.

## Verifying it

Two independent checks were run against the live store:

1. **Token integrity.** For every non-growing session file, the sum of the
   cached buckets was compared with a direct parse of the same file. 338 of 338
   matched exactly on all four token fields and the request count; the one file
   excluded was the live session, still being appended.
2. **Price integrity.** One calendar day was recomputed from raw records with
   hand-written tariff logic: 459,332,806 tokens and $4.257755898 either way.

Re-run the first check by deleting the cache, running the counter, and
comparing `--json` totals against a fresh parse of any single log.
